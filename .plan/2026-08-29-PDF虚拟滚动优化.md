## 背景

当前 `PdfViewer` 已具备：

- 连续长卷滚动（多页上下排列）
- 当前页 ±2 页预渲染（`PDF_PAGE_RENDER_BUFFER`）
- `devicePixelRatio` 高清 canvas
- 目录 / 书签 / 节导航 **instant 跳转**（`behavior: 'auto'`）
- 工具栏相邻页 **smooth 短距滚动**

**仍存在的体验上限**（500+ 页 PDF 尤其明显）：

| 现象 | 根因 |
|------|------|
| 快速甩滚出现空白占位 | 仅渲染窗口内 5 页，远处为占位 div |
| 滚动不够「跟手」 | 518 个页锚点全在 DOM，布局与 scroll 监听有开销 |
| 跳转后偶发高度偏差 | 占位高度为估算值，目标页尚未渲染完 |
| 内存随 DPR × 页数上升 | 高清 canvas 无 LRU 缓存淘汰 |

VS Code PDF 插件更接近：**虚拟列表 + 可见区渲染 + 缓存复用**。本计划目标是对齐该体验，**按需实施**，不阻塞当前 MVP。

---

## 目标

1. **虚拟滚动**：DOM 中仅挂载「可见页 ± buffer」，滚动条总高度由页高数组推算
2. **渲染缓存**：已渲染页 bitmap / canvas 或 ImageBitmap  LRU 缓存，回滚时不重绘
3. **跳转稳定**：目录 / 书签跳转 instant，且目标页优先渲染后再对齐 scrollTop
4. **可选降级**：低内存或超大 PDF 时降低 DPR 或缩小 buffer

**非目标**（本计划不做）：

- 替换 pdf.js 为 Chromium 内置 PDF 插件
- PDF 全文搜索
- 双页并排 / 印刷排版模式

## 架构草案

```
PdfViewer
├── usePdfVirtualScroll()      # 可见范围、scrollTop ↔ 页码、总高度
├── usePdfPageCache()          # LRU：pageNum + scale + dpr → 渲染结果
├── PdfVirtualPageList.tsx     # 只 render visibleStart..visibleEnd
└── PdfPageView.tsx            # 单页 canvas + textLayer（已有，可复用）
```

### 虚拟滚动核心

```typescript
interface VirtualPdfPageMetrics {
  pageNumber: number
  cssHeight: number   // scale 后的 CSS 高度
  cssWidth: number
  offsetTop: number     // 在虚拟列表中的累计 top
}

// scrollTop + viewportHeight → visiblePageRange
// totalScrollHeight = sum(pageHeights) + gaps
```

- 首次打开：并行采样各页 `getViewport({ scale: 1 })` 高度，或懒加载「滚到才量」
- 滚动时：`translateY` 偏移 + 绝对定位可见页，或 spacer + 少量 DOM 节点
- Buffer：建议 `visible ± 3`（可配置），比当前固定 5 页全量锚点更省

### 渲染缓存

- Key：`${fileFingerprint}:${page}:${scale}:${dpr}`
- Value：`ImageBitmap` 或离屏 canvas 引用
- 上限：如 20 页 / 128MB，超出 LRU 淘汰
- 缩放变更：整缓存失效或按 scale 分桶

### 跳转策略（与产品约定一致）

| 操作 | 行为 |
|------|------|
| 滚轮 / 触控板 | 浏览器原生滚动 |
| 工具栏 ← → 相邻页 | `smooth` |
| 目录 / 书签 / footer 节导航 | `auto` instant |
| 跨页 > 1 | 必须 `auto`，禁止 smooth |

## 风险与对策

| 风险 | 对策 |
|------|------|
| 页高不一致导致 scroll 漂移 | 渲染完成后修正 anchor；优先缓存实测高度 |
| ImageBitmap 内存占用 | LRU + 上限；远页只保留低 DPR 缩略 |
| 文本层与 canvas 错位 | 继续共用 `createPdfPageViewport`，textLayer 用 cssViewport |
| 实现复杂度 | 分 A→B→C 交付，B 完成即可显著改善 |
