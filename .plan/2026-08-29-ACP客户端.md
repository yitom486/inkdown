## 背景与原则

### 为什么要 ACP

| 方案 | 说明 |
|------|------|
| ❌ 自研 Agent 运行时 | 需维护模型调用、工具链、会话状态，与产品核心（编辑/阅读）无关 |
| ✅ **ACP Client** | 编辑器只做 Client 侧：UI + 环境（工作区、文件、终端）+ JSON-RPC 桥接；Agent 由外部进程提供 |

ACP 是 JSON-RPC 2.0 开放标准。首版对接 **[codex-acp](https://github.com/agentclientprotocol/codex-acp)**（`@agentclientprotocol/codex-acp`），后续可扩展 Gemini CLI、Claude 等适配器。

### 首个运行时：codex-acp

| 项 | 说明 |
|----|------|
| 安装 | `bunx -y @agentclientprotocol/codex-acp` 或全局安装；**npm 包已 bundled Codex**，通常无需单独装 Codex CLI |
| 认证 | `OPENAI_API_KEY` / `CODEX_API_KEY`（推荐）；Electron 内设置 `NO_BROWSER=1` 禁用 OAuth |
| 启动命令 | 主进程 spawn：`bunx -y @agentclientprotocol/codex-acp`（或用户配置路径） |
| 不打包进安装程序 | 用户自备 Agent 与 Key；v0.1 安装包不含 AI |

### 固定约束（与 AGENTS.md 一致）

- 主进程管理 Agent **子进程**与 stdio 传输；渲染进程 **禁止**直接 spawn
- 所有跨进程能力走 IPC + `Result<T, AppError>`
- UI 使用 shadcn/ui + Tailwind；会话 UI 状态可用 Zustand，Agent 消息流用 IPC 事件 + 可选 TanStack Query
- 包管理仅用 **Bun**

## ACP 协议要点（Client 职责）

依据 [官方 Overview](https://agentclientprotocol.com/protocol/overview)：

| 阶段 | Client → Agent | Agent → Client |
|------|----------------|----------------|
| 初始化 | `initialize`（版本/能力协商） | 返回 Agent capabilities |
| 认证 | `authenticate`（若 Agent 要求） | — |
| 会话 | `session/new` 或 `session/load` | — |
| 对话 | `session/prompt` | `session/update` 通知（流式 chunk、工具调用、plan） |
| 中断 | `session/cancel` 通知 | — |

**Client 必须实现的 baseline 回调（Agent 会反向调用 Client）：**

- `session/request_permission` — 工具/写文件等操作前征求用户同意（MVP 可简化为对话框 Allow/Deny）

**首版可选、后续迭代：**

- `fs/readTextFile`、`fs/writeTextFile`（与现有 `file-service` 复用）
- `terminal/*`（Electron 内嵌终端或 defer）
- MCP 服务器注入（`session/new` 参数，P2）

**协议版本策略：**

- MVP 锁定 **protocolVersion: 1**
- v2 draft 仅做调研项，不在首版阻塞

| 层 | 做法 |
|----|------|
| 面板壳（连接、运行时、cwd、权限） | **自研**（已有 `AgentPanel`），与 ACP 状态机绑定，无现成替代 |

| 消息列表 / Markdown / 代码块 / 流式光标 | **优先现成散装库**，例如 `@assistant-ui/react` 或 `react-markdown` + `shiki`；**不要**自研完整聊天气泡系统 |
| 禁止 | 整仓搬 Continue / Cline / 另一套 IDE Agent 壳 |

原则：**壳自研、皮复用**。新增 UI 前先查 shadcn 与现有 `src/components/ui/`。

### 本地 Codex「已登录」到底是什么（和 Zed / VS Code 一致）

业界**不是**各自偷偷扫任意路径，而是共用 **Codex 官方凭证存储**：

| 产品 | 做法 |
|------|------|
| **Codex CLI** | `codex login` → 写入 `%USERPROFILE%\.codex\auth.json` 或 OS 钥匙串（`cli_auth_credentials_store`） |
| **VS Code Codex 扩展** | 与 CLI **共享同一套** `~/.codex` 缓存；一边登录两边可用，一边 logout 两边失效 |
| **Zed** | 通过 **codex-acp**（如 `@zed-industries/codex-acp` / 官方 `@agentclientprotocol/codex-acp`）：`initialize` 返回 `authMethods`，Client 调 `authenticate`；ChatGPT OAuth 由 Agent 调 `codex_login` 写回 **同一 Codex home**；已登录则直接成功 |
| **Cursor** | 自有 Agent 栈；若对接 Codex 生态，同样落在 Codex home / 环境变量，而非编辑器私有平行账本 |

结论：**可以、也应该「复用本地 Codex 登录态」**——方式是让子进程使用默认 `CODEX_HOME`（`~/.codex`），并走 ACP 认证协商；**不是** Inkdown 自己解析 token 再塞进请求。

### Inkdown 推荐实现（对齐 Zed 模式）

```text
点「连接」
  → spawn codex-acp（继承 env；勿盲目永久 NO_BROWSER=1，否则去掉 ChatGPT 登录项）
  → initialize → 看 authMethods
  → 若 Agent 已能用本地 auth（已 login）：直接 session/new
  → 若需要认证：弹出对话框列出 authMethods
        ├─ Login with ChatGPT  → authenticate({ methodId: 'chatgpt' })，允许本机浏览器
        ├─ CODEX_API_KEY / OPENAI_API_KEY → 用户输入后写入进程 env 或引导写入 Codex 存储后 authenticate
        └─ 可选：主进程 preflight `codex login status` / 检测 auth.json 是否存在（仅布尔提示，不把 token 读进渲染进程）
```

| 要做 | 不要做 |
|------|--------|
| 检测「是否已有 Codex 登录」（status / 文件是否存在）给 UI 提示 | 把 `auth.json` 内容读进渲染进程或日志 |
| 未登录时弹出 **ACP authMethods** 选择（订阅 OAuth / API Key） | 自建平行 Key 库当唯一真相（最多作 UI 临时输入，再交给 Agent/`codex login`） |
| 评估默认改用与 Zed 同系的 `codex-acp` 包，认证 UX 更完整 | 长期 `NO_BROWSER=1` 卡死 ChatGPT 订阅登录 |

| Agent 未安装或版本不兼容 | `agent-registry` + 连接前 preflight（`which` / `--version`）；UI 展示安装指引 |
| stdio 阻塞 / 大 payload | 行缓冲 JSON-RPC；单线程读写队列；超大文件 read 限制 |
| Windows 路径与 ACP「绝对路径」要求 | 统一 `path.resolve`；Client 回调内校验前缀在工作区内 |
| 子进程僵尸 | `window-all-closed` / `before-quit` 与 `process-manager.disposeAll()` |
| 协议演进 v1→v2 | 抽象 `AcpProtocolAdapter` 接口，v1 首实现 |
